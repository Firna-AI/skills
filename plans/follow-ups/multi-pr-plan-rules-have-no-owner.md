# Plan rules for several pull requests are scattered

- **Severity:** Medium. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-28, from the branch `calummoore/do-not-open-pr-planning-aesi`, review round 1, finding 2 (the wider fix that was split off), with two problems that its finding checks found.
- **Location:**
  - `skills/plans/SKILL.md`: "Creating a plan" (the bullets about the status paragraph and a new plan), "Milestones" (the `Depends on:` bullet), "TODOs" (the closing TODOs), "Completion boundary", and "Deleting the plan".
  - `skills/plans/references/deleting-a-plan.md`: the first paragraph and "When".
  - `skills/plans/templates/plan.md`: the status line and "Milestone N".
  - `skills/finish-work/SKILL.md`: step 4 (the new-plan bullet) and step 6 (the first bullet).
  - `skills/delegating/SKILL.md`: the first paragraph of "Workspaces across machines", the primary-branch bullet below it, step 4 and step 6 of "Check, merge, and continue" ("the final pull request"), and the checklist line about the final pull request.
  - `skills/delegating/references/workspaces.md`: the last paragraph of "Integrate and close".
- **Reason:** The direct fix is in the branch above, and this wider fix reaches areas that the branch did not change, such as "TODOs" in the `plans` skill and the primary-branch rules of the `delegating` skill.

- **Terms:**
  - **Plan:** a file under `plans/` that records the milestones and TODOs of one change. The `plans` skill owns it.
  - **Plan with several pull requests:** a plan whose work goes into `main` in more than one pull request, for example because a release must come between two parts. `deleting-a-plan.md`, "When", allows it: each earlier pull request keeps the plan, and the last one deletes it.
  - **Closing TODOs:** the last TODOs of a pull request's work: the gate, the commit and push, the review, keep or delete the plan, and open the pull request.
  - **Primary branch:** the branch of a plan that runs in several workspaces. Workspace branches merge into it, and only it merges into `main`. The `delegating` skill defines it.
  - **Completion boundary:** the merge that ends a set of milestones. Every required TODO before it must be possible before that merge.
- **Background:**
  - On 2026-11-28 an agent opened mokly-ai/mokly#608, a pull request that held only a new plan. The user closed it with "do not open the PR in the planning stage" and "PR should open when impl completes". The user chose on 2026-11-28 to fix this in the skill bodies, with no new always-on line in `global/AGENTS.md`.
  - After that branch, `finish-work` step 6 owns the rule for when a pull request opens. `finish-work` step 4 and "Creating a plan" in the `plans` skill restate it for a new plan. For a plan with several pull requests, step 6 says that each pull request has its own pull request TODO, and it counts only the milestone TODOs before that TODO.
  - The same branch added a direct fix to "Completion boundary". When the work spans more than one pull request, the merge of each pull request is the completion boundary of the milestones before its pull request TODO. A later milestone can name that merge on its `Depends on:` line. "Workspaces across machines" in the `delegating` skill starts such a milestone only after that pull request merges into `main`.
  - The same branch added a checklist line to `skills/writing-skills/SKILL.md`: a rule restated in another step, template, or reference of the same skill says what the source says, or points to it. That line catches a new copy at the time of writing. It does not remove the copies that exist.
- **Problem:**
  - The rules for a plan with several pull requests have copies in the files under **Location**, and some copies hold for one pull request only. Commit `77fadd6` added the delegating text for one pull request into `main`. The branch above had to correct three sentences that held for only one shape: one pull request, several pull requests, or an early pull request that the user asks for.
  - "TODOs" in the `plans` skill and "Milestone N" of the template give the closing TODOs only for the last pull request. They do not say where the pull request TODO of an earlier pull request goes. The Mokly plan of #608 wrote a closing milestone of its own for its first pull request.
  - An older plan has no pull request TODO for an earlier pull request. Then the count of `finish-work` step 6 has no TODO to stop at, and the agent holds that pull request until every milestone is done.
  - The primary-branch bullet of the `delegating` skill says: "Its pull request into `main` is the completion boundary from the `plans` skill. That pull request deletes the plan, as that skill says. After that merge, delete the primary branch and archive its workspace." The last paragraph of `workspaces.md` says the same. For an earlier pull request of a plan with several pull requests, the plan stays, and the next pull request needs a branch. Step 6 of "Check, merge, and continue" says that a blocking finding closes "before the final pull request merges", which does not say which merge.
  - The status line: "Completion boundary" says to replace the branch sentence with `[PR #<number>](<url>) is open.` when a pull request opens and the plan stays. After that pull request merges, the plan on `main` says "is open" about a merged pull request. The next pull request starts on a new branch, and no rule writes that branch into the status line.
- **Impact if no action:** The next change to these rules must edit each copy again. A missed copy makes an agent hold a pull request, delete the plan or the primary branch too early, or show a wrong status on `main`.
- **Root question:** How does an agent know which milestones belong to each pull request of a plan, so that each pull request opens and merges when its own milestones are done, the plan stays until the last one, and the plan status stays true?
- **Options:**
  - **A.** Mark each pull request in the plan. In a plan with several pull requests, the milestones of each pull request end with a closing milestone that holds its closing TODOs, as the Mokly plan did. "TODOs" in the `plans` skill states this, and the template shows it as a variant of "Milestone N". An older plan without a closing milestone gets one added before its first pull request opens. Correct the primary-branch bullet and `workspaces.md` to say that only the last pull request deletes the plan and the primary branch. Cost: the status line and the "final pull request" lines stay as they are, so the status part of the root question stays open. Effort: Small.
  - **B.** Do A, and give the rules one owner. One section in `deleting-a-plan.md` owns every rule for a plan with several pull requests. It says which milestones belong to each pull request (up to its closing milestone), that each merge is their completion boundary, and that a `Depends on:` line names an earlier merge as "the merge of the pull request of Milestone <N>". It says that each earlier pull request keeps the plan and the primary branch, and that the last one deletes both. For the status line, it says that the first commit of the next pull request writes its branch into the status line, in place of the link. Every place under **Location** points to that section and stops restating it. Cost: one edit in each file under **Location**. Effort: Medium.
- **Left out:**
  - Dropping plans with several pull requests is left out. It deletes the rule in `deleting-a-plan.md`, which is on `main`, and the Mokly change needs a release between its two pull requests.
  - A script that checks the copies is left out. It adds a new check, and the outcome rules of the `decisions-and-findings` skill block a new check without the user. A script also cannot tell whether two sentences agree.
  - A status line with no branch and no pull request state is left out. It reverses the rule of commit `414ddd5` that the status line names the branch, and that rule is on `main`.
- **Wider fix:** B. One owner keeps one copy of each rule, so the next change edits one place. The `writing-skills` checklist line only asks the writer to keep the copies the same.
