# Model table follows only the Conductor list

- **Severity:** Medium. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Outside the scope.
- **Added:** 2026-11-20, from the branch `calummoore/move-codex-actions-to-gpt-6-2-sol-moco`. Its review listed two problems outside the scope. The lookup rule names `conductor model`, which a Conductive computer does not have. The claude rows name `opus-5-5-1m`, which `conductive models list` does not give. This item holds both, because they share one root question.
- **Location:** `skills/models/SKILL.md`, lines 29 to 32, the lookup rule, and lines 18, 19, 21, 22, and 26, the claude rows. `skills/delegating/SKILL.md`, lines 78 and 79. `skills/delegating/references/conductor.md`, each command block. `skills/brainstorming/SKILL.md`, line 32. `skills/finish-work/references/ci.md`, lines 163 and 198 to 200.
- **Reason:** Each fix changes the rule that names the source of the model ids, and this branch only moves the codex ids.

- **Terms:**
  - **Conductor:** an app that runs agent workspaces and sessions. Its command-line tool is `conductor`.
  - **Conductive:** an app that runs each agent workspace on its own cloud computer. Its command-line tool is `conductive`.
  - **Model list:** the agents, the model ids, and the efforts that an app takes. Each app prints its own list.
  - **Stale table:** the case in the `models` skill where the model list does not give a model of the table. The agent then tells the user and uses the nearest listed model.
- **Background:**
  - `skills/models/SKILL.md` has one table with the agent, the model id, and the effort of each action. Skills and plans name the action, not the model id.
  - Lines 29 to 32 of that file say: "The model ids are the ids that `conductor model` lists. When `conductor model` does not list a model of this table, the table is stale. Tell the user. Then use the nearest model that it lists."
  - `skills/delegating/SKILL.md`, lines 78 and 79, say the same about a stale table. `skills/delegating/references/conductor.md` gives each route as a `conductor` command, for example `conductor session create`.
  - `skills/brainstorming/SKILL.md` line 32 names a `conductor` command for work in Conductor. `skills/finish-work/references/ci.md` lines 163 and 198 name `conductor` commands with no app condition.
  - On 2026-11-20, a Conductive cloud computer had no `conductor` command. Its tool `conductive` printed the model list with `conductive models list`.
  - That list gave the codex ids `gpt-6.2-sol`, `gpt-6.2-astra`, `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6.1-terra`, and `gpt-6-luna`. It gave the claude ids `claude-opus-5-5`, with the label "Opus 5.5", `claude-sonnet-5-5`, `claude-haiku-5-5`, and `claude-fable-5-2`. It did not give `opus-5-5-1m`.
  - The five claude rows of the table name `opus-5-5-1m`. These are `brainstorming`, `default orchestrator`, `ui implementor`, `docs implementor`, and `second-pass review agent`. The four codex rows name `gpt-6.2-sol`.
  - In Conductive, `conductive sessions create --agent <agent> --model <model> --effort <effort> --title <text> --message <text>` starts a session. On 2026-11-20, a codex review session that started this way ran on `gpt-6.2-sol` at `max`.
  - Nobody checked which ids and labels `conductor model` gives, or whether Conductive takes `opus-5-5-1m`. Branches named `conductor/...` still merged into `main` on 2026-11-20, so the skills probably still run in Conductor too.
  - On 2026-11-20, Cal had a question open about the claude id `opus-5-5-1m`. This item records the problem. It does not answer that question.
- **Problem:** In Conductive, an agent cannot run the lookup that the `models` skill names. When the agent reads `conductive models list` instead, the five claude rows look stale, because that list names Opus 5.5 `claude-opus-5-5`.
- **Impact if no action:** Each agent in Conductive that checks the table first finds no `conductor` command. Then it reports a stale table to the user, or it passes a claude id that nobody checked in Conductive.
- **Root question:** How does an agent in each app find the model id that its app takes for each action?
- **Options:**
  - **A.** Change nothing. In Conductive, an agent must find the list command by itself. With `conductive models list`, it reports the claude rows as stale and uses `claude-opus-5-5`, the nearest listed model. The user gets that report at each claude delegation in Conductive. Effort: Small.
  - **B.** Name the list command of each app in the lookup rule of `models` and in the stale-table line of `delegating`. These are `conductor model` in Conductor and `conductive models list` in Conductive. Keep the ids. In Conductive, the claude rows still look stale. Effort: Small.
  - **C.** Do B. Also give each claude row the id of each app, for example `opus-5-5-1m` for Conductor and `claude-opus-5-5` for Conductive. The table then gives an id for each list, and it stays the one place that changes with a model. Each claude model change then edits two ids. Effort: Small.
  - **D.** Do B. Also name each model by its label in the model list, such as "Opus 5.5". The agent then takes the id from the list of its app. Each delegation then needs one more lookup. Nobody checked the labels of `conductor model`, so one label may not fit both apps. Effort: Small.
  - **E.** Make Conductive the only app of the skills. Name only `conductive` commands in each location above, and change the claude ids to `claude-opus-5-5`. A session in Conductor then has no lookup and no route that works. Effort: Medium.
  - **F.** Do C. Also move every app command into one route reference for each app under `skills/delegating/references/`: the present `conductor.md` and a new reference for Conductive. The lookup rule of `models`, `brainstorming`, and the CI reference of `finish-work` then point to the reference of the app. A change in one app then edits one file. Effort: Medium.
- **Left out:** A script that finds the app and prints its model list. It adds a tool to keep current, and B gives the same with one sentence. A check in the gate that compares the table with a model list. The gate runs in CI without the apps, so it cannot read a list.
- **Wider fix:** F. One route reference for each app holds every command of that app, so a change in one app edits one file.
- **Previous examples:** `77fadd6` moved the routes of each action from the `models` skill into the `delegating` skill. The lookup command stayed in `models`.
