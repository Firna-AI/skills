# Read-only agents cannot run a spike

- **Severity:** Low. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-28, from the branch `calummoore/spike-tests-for-unsure-ai-v6g1`, review round 1, the wider fix of finding 1.
- **Location:**

  - The prompts that say "Do not modify files": `skills/implementation-review/references/review-prompt.md` line 37, `skills/implementation-review/references/check-prompt.md` line 37, `skills/implementation-review/references/second-pass-prompt.md` line 34, and `skills/plans/references/follow-up-items.md` line 75.
  - The lines that restate that these agents are read-only: `skills/implementation-review/SKILL.md` lines 10 and 39, `check-prompt.md` lines 6 and 11, `second-pass-prompt.md` lines 4, 14, and 33, `review-prompt.md` lines 28 and 29, `skills/plans/SKILL.md` line 58, `follow-up-items.md` line 70, and `skills/finish-work/SKILL.md` line 77.

- **Reason:** Options B, C, and D change the review and check prompts on `main`, and the user decision of 2026-11-28 covers only the always-on spike rule and edits to the `brainstorming` and `testing` skills.

- **Terms:**
  - **Spike:** a small throwaway experiment that checks how a library, a tool, an API, a platform, or existing code behaves. Its files stay under the git-ignored `.context/` directory, and it is never committed.
  - **Read-only agent:** a delegated agent whose prompt says "change nothing" or "Do not modify files". The first-pass reviewer, the finding checks, the options check, and the follow-up item check are read-only agents.
  - **First-pass reviewer:** the agent that reviews the diff of a branch and returns numbered findings, as `skills/implementation-review/SKILL.md` says. It runs as Codex.
  - **Finding check:** a fresh agent that confirms or removes one finding of a review before the working agent fixes it.
  - **Working agent:** the session that runs the review of a branch and applies the fixes.
- **Background:**
  - On 2026-11-28 the user chose to add an always-on rule to `global/AGENTS.md`, under `## Working`: "Before you build on how a library, a tool, an API, a platform, or existing code behaves, check it in its docs or its code. When they do not settle it, run a spike: a small throwaway experiment under `.context/`. Keep its command and output there. Do not commit a spike." The decision rejected three other places for the rule: only the `testing`, `brainstorming`, and `plans` skills; evidence for each premise of a decision; and a new `spikes` skill.
  - The same change lets a brainstorm run a spike under `.context/<topic>/`. Commit `c67a5fa` (#43) had added the ban "Do not build a mockup or a spike." to `skills/brainstorming/SKILL.md`, and commit `9c20d29` removed it.
  - The problem that started this item: step 3 of `skills/brainstorming/SKILL.md` told the brainstorm delegate only to "change nothing". `skills/delegating/SKILL.md` uses that phrase for fully read-only work, so the delegate could not write spike files. The source branch fixed that brief. It now tells the delegate "to change nothing in the repository and to keep each spike under `.context/<topic>/`".
  - `skills/delegating/SKILL.md` says: "A read-only agent, such as a reviewer, gets 'change nothing'." The four prompts in **Location** say "Do not modify files".
  - In review round 1 of the source branch, the working agent ran the first-pass reviewer by hand as `codex exec -m gpt-6.2-sol -s read-only`. Its log says `approval: never` and `sandbox: read-only`. That sandbox blocks every file write, also under `.context/`. Round 2 ran as a Conductive session. Nobody checked which sandbox such a session gets.
  - An earlier design call of the same day kept the finding check sentence "When you are not sure, confirm it" unchanged. Its reason was that the always-on rule reaches the checker through the global file.
- **Problem:** A read-only agent that is not sure how a tool behaves cannot write the files of a spike. Its prompt forbids every file change. A Codex reviewer that runs with `-s read-only` also cannot write any file. So the always-on rule reaches these agents, but they cannot follow it.
- **Impact if no action:** A reviewer can raise a finding that rests on an unchecked guess about how a tool behaves. A finding check that is not sure confirms the finding, as `check-prompt.md` lines 79 and 80 say ("When you are not sure, confirm it"). The guess then goes into the fix round as a confirmed finding, unless the working agent notices it and runs the spike itself.
- **Root question:** How does a reviewer or a check settle how a tool or the code behaves before it raises, confirms, or removes a finding?
- **Options:**
  - **A.** Change nothing. No rule asks a read-only agent to mark an unchecked premise, so the working agent must find such guesses itself. Effort: Small.
  - **B.** Keep the agents read-only. Ask each read-only agent to mark, in its report, each premise about tool or code behaviour that it did not check. Add that line to `review-prompt.md`, `check-prompt.md`, `second-pass-prompt.md`, and the prompt in `follow-up-items.md` lines 74 to 87. Then the working agent runs a spike for each marked premise: before the fix round, as a new sentence in step 1 of "After the review" in `skills/implementation-review/SKILL.md`, and before the commit for a follow-up item check or a plan options check. Effort: Small.
  - **C.** Give every read-only brief one exception. In `skills/delegating/SKILL.md`, a read-only agent gets "change nothing, except a spike whose files all stay under the `.context/` directory that the brief names". The four prompts and every line in **Location** use the same words. Each check names its own folder, because checks run side by side in one working tree. The Codex reviewer then needs a writable sandbox, such as `-s workspace-write`, which lets it write anywhere in the working tree. `screenshots.md` must say whether a reviewer may then take pictures. Effort: Medium.
  - **D.** Give every read-only agent its own git worktree, as `skills/delegating/SKILL.md` "Subagents in one session" describes, and allow spike files there. A worktree is a separate checkout directory. It is not a write limit: the launch of the agent sets what it can write. No session command sets a sandbox, a working directory, or a worktree, so a read-only sandbox also blocks a spike in the worktree, and a writable sandbox reaches the whole working tree, as in C. A linked worktree also shares the refs, the objects, and the config of the repository, so a git write there can move the branch under review. The working agent must commit first, because a worktree holds only committed content, and it must remove each worktree after the check. Some read-only agents run before the commit: the follow-up item check (`follow-up-items.md` line 69) and the plan options check (`second-pass-prompt.md` lines 15 and 16). `check-prompt.md` line 18 says "A check needs no second checkout." D must change both. Nobody has checked whether `codex exec -C <worktree> -s workspace-write` keeps writes out of the original checkout. Effort: Medium.
- **Left out:**
  - A spike exception in the always-on rule itself. It costs context on every turn, and it would cancel a read-only instruction that a user gives through a brief.
  - A separate workspace on its own machine for each reviewer and check. It breaks the rule in `skills/delegating/SKILL.md` lines 66 to 68 that the first session of a workspace runs every other action of the work, a review included, inside the workspace. It also costs a machine start and an archive for each agent, and a push from that machine can still change the remote branch.
  - A spike in a temporary directory outside the repository. It breaks the always-on rule that the user chose on 2026-11-28, which puts each spike under `.context/`.
- **Wider fix:** C. It gives every read-only brief one rule for spike files.
- **Previous examples:** The brainstorm ban that `c67a5fa` added and `9c20d29` removed. Under that ban, a brainstorm delegate wrote "I did not run a check, because line 15 forbids one" about how a scratch Cargo package builds.
